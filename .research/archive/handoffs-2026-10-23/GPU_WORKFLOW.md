# GPU discovery workflow after the October 23 correction

Research remains paused. This changes the saved execution order;
it does not authorize restarting research or provisioning a worker.
Read this with GOAL.md, STATE.md, ROUTES.md and GPU_BUDGET.json.

## What went wrong

The research repeatedly derived a sufficient condition, refuted a
strong universal version, and handed off another nearby condition.
The validated GPU operator and successful integrated cycle were
then treated as optional future infrastructure. New proof notes
displaced the intended computational feedback. A completed GPU
experiment must now precede another sequence of proof-route changes.

## First milestone after the user resumes

Complete a NEW adversarial derive-test-certify-review cycle with
the existing device-resident Fourier operator. Reuse old Singer
fixtures only for regression. Do not repeat their size trend as
the main experiment. The default first target is the already
recorded arbitrary-support OP140 inequality: seek small normalized
J=c^T(C+2sqrt(n)I)^(-1)c/sqrt(n) on genuine Boolean supports in
its actual-low-M domain. Its threshold is1/140, not a newly asserted
theorem. The saved full-residual verifier is the CPU certification
baseline. Consult its exact conventions rather than inventing a
new normalization. This is an adversarial test of the existing gap,
not a claim that restating it constitutes mathematical progress.

Preparation must include new reproducible adversarial inputs, not
only already-settled construction controls. Use changes to support
as well as broad witness directions. Preserve known all-circle M
upper bounds when a transformation permits it. Mark every other
low-M screen heuristic until its actual premise is certified. A
numerically weak witness alone is not a falsifier of OP140 or Chowla.

The advisor may identify a better precise GPU-suitable target during
this preparation. It must have an explicit objective and mathematical
failure condition. Replacing OP140 does not remove the requirement
to execute the feedback cycle or reopen a refuted architecture.

## Execution requirements

1. Define one quantitative claim, the adversarial variables, a finite
   search budget, a certifiable failure condition, and what each
   outcome would change. Cap initial exploratory paper work at
   30 minutes of wall time after reading the handoff. Implement
   the experiment next. Do not start a second proof route instead.
2. Reuse src/cstar_gpu_kernel.py and, where appropriate,
   src/cstar_gpu_projected.py. Keep Fourier vectors and repeated
   actions resident on the device. The existing operator batches
   vectors for a FIXED A; changes to A need explicitly tested
   operator updates. Do not claim that feature already exists.
3. Build and test the actual new runner on Dirichlet through dirun.sh.
   Check independent small exact actions, dimensions/aliasing,
   input distinctness and the intended optimization constraints.
   A CPU failure is an implementation task to repair, not a reason
   to begin another theoretical detour.
4. Refresh the provider balance and worker inventory before launch.
   Use one bounded RunPod job within the EXISTING cumulative cap,
   minimum balance, 30-minute/$1 per-run limits, and cleanup rules.
   No top-ups or new billing commitments. If access or budget blocks
   deployment, report that actual external blocker and preserve the
   runnable packet; do not quietly substitute a paper-only milestone.
5. Use GPU output to choose CPU exact follow-up. For a claimed
   counterexample, certify BOTH the inequality violation and its
   all-circle low-M premise. For a witness, certify the appropriate
   exact a,Q,H or residual bound. A failed optimizer does not give
   a global lower bound on the whole witness space.
6. The advisor reviews the resulting mathematical evidence, challenges
   its scope and identifies the next test or lemma. A theorem is not
   required for the cycle to be informative, but a larger collection
   of passing controls is not sufficient. State what changed and
   what the experiment could not distinguish.
7. Retrieve outputs, delete only this project's GPU worker, verify
   deletion, update the cumulative budget and save a resumable packet.
   Never shut down shared Dirichlet.

## Observable acceptance criteria

The first resumed checkpoint must link to:

* The runnable new experiment, configuration, seeds and input hashes.
* A terminal GPU run record, including its real search scope, outputs,
  timing, spending and verified worker cleanup.
* Exact CPU validation of consequential outputs, or an explicit
  certification failure retained with the numerical proposal.
* An advisor decision tied to those outputs and the full Chowla goal.

No claim of end-to-end acceleration follows from the old warmed
matvec timing alone. Record end-to-end time for the new experiment.
Do not spend the budget merely to produce a GPU activity log.

## Cadence after the first cycle

Keep computation and proof interleaved. Do not run two consecutive
paper-only exploratory goal turns while a discriminating experiment
is available and GPU resources remain authorized. A short exact proof
or finite certification should be completed when ready; that exception
does not authorize opening another speculative proof chain. After a
failed claim, let its actual counterexample drive the next experiment
before adding a nearby sufficient condition.

Keep both the universal-witness and genuine construction tracks in
the experimental queue. A construction experiment needs an all-circle
UPPER-bound follow-up. Preserve refuted routes and scope limits.
When GPU funds are exhausted, continue discovery computationally on
Dirichlet under the existing authorization and report the limitation.

These rules are an execution commitment, not evidence that a future
experiment has already happened or a guarantee of solving Chowla.
